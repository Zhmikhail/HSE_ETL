# Отчет о выполнении экзаменационной работы Юрков Михаил

## Паспорт работы

| Параметр | Значение |
| --- | --- |
| Тематика данных | YouTube trending, продовольственные цены, события поставок |
| Хранилище исходной таблицы | Yandex Database |
| Перенос данных | Yandex DataTransfer |
| Batch-обработка | Yandex Data Processing и Apache Airflow |
| Streaming-обработка | Apache Kafka и PySpark |
| Визуализация | Yandex DataLens |

Работа оформлена как последовательная проверка четырех облачных механизмов:
перенос данных, пакетная обработка, потоковая обработка и визуализация. Для
каждого этапа фиксировались входные данные, способ выполнения и контрольный
результат.

## 1. Проверка переноса YouTube-данных через DataTransfer

### 1.1. Исходная таблица

В качестве исходной таблицы использован набор YouTube trending. Он включает
описание ролика, канал, категорию, дату публикации и метрики вовлеченности:
просмотры, лайки, дизлайки и комментарии.

Объем подготовленного набора превышает 30 МБ. Для загрузки в YDB добавлено поле
`row_id`, так как один и тот же ролик может встречаться в данных несколько раз.

### 1.2. Факт загрузки и первичный контроль

В YDB создана таблица `ru_videos_raw`. После импорта выполнены контрольные
запросы:

- подсчет общего количества строк;
- подсчет уникальных видео;
- поиск максимального значения просмотров;
- агрегирование по категориям.

### 1.3. Передача в объектное хранилище

Для DataTransfer настроена пара endpoint: YDB как источник и Object Storage как
приемник. Успешное появление выгрузки в бакете принято как подтверждение
работоспособности переноса.

### 1.4. Регламент выполнения

Порядок выполнения зафиксирован в виде регламента:

| Шаг | Действие | Контроль |
| --- | --- | --- |
| 1 | Создать базу YDB | база доступна в консоли Yandex Cloud |
| 2 | Создать таблицу `ru_videos_raw` | таблица отображается в YDB |
| 3 | Загрузить подготовленный CSV | импорт завершается без ошибок |
| 4 | Выполнить проверочные YQL-запросы | видны количество строк и агрегаты |
| 5 | Создать endpoint источника | endpoint указывает на YDB |
| 6 | Создать endpoint приемника | endpoint указывает на Object Storage |
| 7 | Запустить transfer | статус transfer становится успешным |
| 8 | Проверить бакет | в Object Storage появляются выгруженные данные |

Особенность набора данных: один ролик может встречаться в разные даты. Поэтому
для первичного ключа использован отдельный технический идентификатор `row_id`.

## 2. Регламент batch-обработки продовольственных цен

### 2.1. Характеристика входных данных

Второй блок основан на данных о мировых продовольственных ценах.

| Показатель | Значение |
| --- | --- |
| Формат | CSV |
| Размер | 53 МБ |
| Количество строк | 419527 |
| Требование задания | не менее 50 МБ |

### 2.2. Описание преобразований

В рамках Spark-обработки выполняются следующие операции:

- чтение данных из Object Storage;
- применение фиксированной схемы;
- преобразование даты наблюдения;
- выделение месяца;
- очистку таблицы цен;
- расчет страновых агрегатов;
- расчет товарных агрегатов;
- расчет месячной динамики;
- расчет агрегатов по рынкам.

На выходе формируется набор таблиц `prices_clean`, `country_stats`,
`commodity_stats`, `monthly_stats` и `market_stats`.


### 2.3. Регламент выполнения

Порядок выполнения batch-части:

| Этап | Описание |
| --- | --- |
| Подготовка Object Storage | входной CSV и PySpark-задание загружены в бакет |
| Настройка DAG | указаны подсеть, сервисный аккаунт, SSH-ключ, бакет и Metastore |
| Запуск Airflow | DAG создает временный кластер Data Processing |
| Выполнение Spark | PySpark-задание читает CSV и строит витрины |
| Регистрация таблиц | результаты сохраняются через `saveAsTable(...)` |
| Очистка ресурсов | временный кластер удаляется после завершения |

Проверка завершения выполнялась по двум признакам:

- в Object Storage появились выходные директории с Parquet-данными;
- в Hive Metastore зарегистрированы таблицы `prices_clean`, `country_stats`,
  `commodity_stats`, `monthly_stats` и `market_stats`.

Для регистрации таблиц использовался Hive Metastore. Подключение передавалось в
свойствах Spark, после чего результаты стали доступны как Spark SQL-таблицы.

## 3. Потоковая часть: события поставок в Kafka

### 3.1. Структура сообщений

Третья часть построена на событиях продовольственных поставок в формате JSON
Lines.

| Показатель | Значение |
| --- | --- |
| Объем | 22 МБ |
| Количество сообщений | 38237 |
| Topic | `food-supply-events` |

Содержательно сообщение описывает состояние поставки: рынок, товар, цену,
валюту, запас, поставщиков, контроль качества и риск.

### 3.2. Схема обработки потока

Потоковый сценарий разделен на два этапа:

1. запись JSON-сообщений в Kafka topic;
2. чтение topic в PySpark Streaming, разбор вложенного JSON и сохранение
   результата в плоском виде.

После flatten-обработки остаются аналитические поля страны, рынка, товара,
категории, цены, запасов, поставок, проверок качества и риска.

### 3.3. Регламент выполнения

Kafka-сценарий выполнялся по следующему регламенту:

| Этап | Параметры |
| --- | --- |
| Загрузка входа | JSONL-файл и PySpark-задания размещаются в Object Storage |
| Подготовка Kafka | создается topic `food-supply-events` |
| Доступы Kafka | создается пользователь с правами на чтение и запись |
| Writer job | Data Processing отправляет JSON-сообщения в topic |
| Reader job | Structured Streaming читает topic и разбирает JSON |
| Checkpoint | задается отдельный путь для служебного состояния Spark |
| Результат | плоская таблица сохраняется в Object Storage |

При запуске передавались bootstrap servers Kafka, topic, учетные данные
пользователя, output-путь и checkpoint-путь. Checkpoint использовался как
служебная область Spark Streaming.

Критерии приемки результата:

- задание записи сообщений завершилось успешно;
- задание чтения Kafka topic завершилось успешно;
- в результате появились поля `event_id`, `country_iso3`, `market_id`,
  `commodity`, `usd_value`, `stock_level_days`, `shipment_tons`,
  `quality_check_status`, `risk_level` и `risk_reason`.

## 4. Подготовка визуального слоя в DataLens

Визуализация разделена на два dashboard: отдельная страница для медиаданных и
отдельная страница для продовольственного мониторинга.

### 4.1. Подготовка датасетов

Перед построением графиков выполнялась проверка датасетов:

| Проверка | Назначение |
| --- | --- |
| Первая строка содержит заголовки | DataLens корректно называет поля |
| Кодировка UTF-8 | русские названия и текст отображаются без искажений |
| Разделитель запятая | таблицы корректно разбиваются на колонки |
| Числовые типы | метрики можно суммировать и усреднять |
| Даты | временные графики строятся в правильном порядке |
| Логические поля | признаки отключенных комментариев и рейтингов используются как фильтры |

Для YouTube-части использована облегченная таблица без длинных текстовых полей.
Это снизило риск ошибок при загрузке и оставило только поля, необходимые для
графиков. Для числовых полей при необходимости использовалось явное приведение
типов.

### 4.2. Dashboard YouTube Trending Analytics

Назначение страницы - оценить активность видео и каналов.
